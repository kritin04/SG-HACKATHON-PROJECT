CHANGE IMPACT COPILOT: APP WALKTHROUGH & DEMO VIDEO SCRIPT
==========================================================

  Who this is for: the team (to understand every screen) and whoever records the demo video.
  Audience of the video: managers and executives (the why) plus developers (the how), so every scene has a one-line business message and a one-line "how it works".

0. THE STORY IN 30 SECONDS
--------------------------

  "Before anyone writes code, a bank has to know what a change will affect: which systems, which data, which teams, which approvals. Today that takes several people hours or days of manual digging. The Change Impact Copilot does it in minutes. It reads the Jira ticket, follows a verified map of the real code, uses a local AI to judge exactly what changes and how, and posts the answer back into Jira, with proof for every claim. It runs fully on our laptop: no data leaves the bank."

Three ideas to repeat throughout the video:
1. Before coding: impact is known at the cheapest moment.
2. Proof, not guesses: every item links to the exact line of code or config.
3. Private and local: the AI runs on the laptop; nothing goes to the cloud.

What's real and what's demo data (say it honestly if asked):
- Real: the code we analyse (Google's open-source Bank of Anthos), the map built from it, the Jira Cloud site, the local AI models.
- Demo: the 9 change requests, team owners, outside systems (Regulatory Reporting, CRM…), data-sensitivity labels and approval rules. At a bank these would come from existing registers.

"What changes, and how" (open by default)

- Show checked but not impacted (n): what was considered and ruled out (transparency).

Collapsible sections
  Section  |  Shows
  Data  |  Each table involved: sensitivity labels (🔒 Personal / Financial / Secret), who writes and reads it, new fields (e.g. "New field phone_number · Personal data")
  Outside systems  |  Each outside system: owner, what it does, how it's affected, and actions: ✓ Notify the owner · ✓ Test the interface · ✓ Get sign-off
  Testing  |  Existing automated tests to re-run, per service (expand to see test names) · Test gaps (parts that change but have no test) · Suggested new test scenarios (AI)

  People to involve  |  Owner teams and approvers, with the reason for each
  How this analysis was worked out  |  Where the change starts (entry points) and how each was found (glossary word, name in text, AI, meaning-based search) · the pipeline steps with model and time · a note on git history · "The AI can only judge candidates from the verified map; it cannot invent new ones."

Right column
- Impact on the system: a small map showing only the impacted parts, coloured by verdict, with a legend and Open full map →.
- Why this risk level: the exact reasons that added risk points (personal data, outside systems, approvals, test gaps, API change, open questions, high-criticality parts), the size reason, and analysed at commit · model · local AI time.

The proof drawer ("Why?" / "Show proof")
Slides in from the right:
- "Why is this here?" + title + source badge (Auto-detected / From catalog / Human-confirmed).
- Reason in a blue box.
- Dependency path: the chain followed on the map, e.g. Customer Relationship Management (CRM) → reads (outside system) → users. Links that came from the catalog or the AI are badged.
- Evidence (n): each piece of proof with a type badge (Code, Configuration, Database schema, Jira, Curated catalog…), its file:line @ commit, an ID, and the actual code with line numbers.

5. QUESTIONS JUDGES MAY ASK (SHORT ANSWERS)
-------------------------------------------

  Question  |  Answer
  Is the AI making things up?  |  It can only judge parts found in the verified map. Every claim cites evidence that's checked by code, and anything unproven falls back to rules and is labelled. The map itself scores 49/49 against a hand-made answer key.
  How accurate is the impact analysis?  |  On 9 test tickets against an engineer's answer key: 100% of the parts that should be involved were found, 100% of required approvals and outside systems, and 0 parts wrongly marked "must change". Risk levels match an engineer's view: only the personal-data and new-vendor tickets are High; the vague one is Low with questions. Where it disagrees (e.g. which service carries the main change), a reviewer fixes it with one click.
  Does data leave the bank?  |  No. The AI models run locally (Ollama). Jira is reached only through its API with your token.
  Did you train a model?  |  No training. It uses existing open models with retrieval, structured prompts and verification.
  Will it work on our codebase?  |  Yes for Python and Java services today; other languages plug in the same way. The owners, outside systems and rules would be imported from the bank's existing registers (CMDB, interface catalogue, data register, change policy).
  Why is it slow?  |  It's running on a laptop CPU. On a server or GPU each analysis takes seconds.
  What's real?  |  The code (Google's open-source Bank of Anthos), the map, Jira Cloud and the AI are real. The tickets, owners, outside systems and rules are demo data.

6. TEN-SECOND GLOSSARY
----------------------
  Term  |  Plain meaning
  Change request (CR)  |  A Jira ticket asking for a change
  Service  |  One program in the system (e.g. ledgerwriter records payments)
  API / endpoint  |  A door into a service (e.g. POST /transactions = "record a payment")
  Outside system  |  A system we don't own but which uses our data (e.g. Regulatory Reporting)
  Must change / Likely affected / Re-test only  |  Must be edited / probably needs a look / no edit, but test it again
  Approval rule (control)  |  A bank rule: "if a change touches X, Y must approve"
  Dependency map  |  The picture of what talks to what, built from the code
  Evidence / proof  |  The exact code or config lines behind a claim
  Local AI  |  AI models running on this laptop, not in the cloud
